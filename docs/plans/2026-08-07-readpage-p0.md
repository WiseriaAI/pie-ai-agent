# ReadPage P0 实施计划：先止血，用数据决定要不要 Page Store

日期：2026-08-07
依据：`docs/research/2026-08-07-read-page-token-efficiency.md`
范围：只做该文档的 P0（外加一条实测补充项）。P1 Page Store / P2 检索层**不在本计划内**，等 P0 数据出来再定。

## 为什么只做 P0

真机实测（本分支 `[ctx]` 日志 + IndexedDB 解剖脚本）：

| 观测 | 数值 |
|---|---|
| 单份 atlas | 20881 tokens |
| 其中 484 个 `<control>` | 14483 tokens（**69%**） |
| 结构开销（tag/属性名/引号） | 83522 chars 中 51853 是结构（**62.1%**） |
| 某轮 read_page 后 prompt 增量 | +106411，其中 cached 只 +1280 |
| elide 后历史侧残留 | 4935 tokens（已压 99.3%，不是瓶颈） |
| 每轮固定开销（tools 6118 + system 4613） | 10731 tokens |

结论：**成本几乎全在 read_page 单次返回体的对象基数上**，历史驻留和 cache 都已经不是主要矛盾。P0 的头两片直接打这个 69%。

Page Store 是好方向，但它在 MV3 下有未解决的生命周期问题（现状 `page-atlas/state.ts` 是 SW 内存 `Map` + 120s TTL，SW 被 kill 后 `page_ref` 会成批失效），值得等 P0 数据再评估是否要付这个复杂度。调研文档保留为迭代方向。

## 切片

每片独立可验证、独立可回滚。顺序即实施顺序。

---

### 切片 0 — 分段观测（先有基线）

对应 P0.7。**必须最先做**，否则后面几片的收益无法归因。

**改**：`src/lib/agent/tools/read-page.ts` handler 返回前加一条 `console.log("[read_page]", {...})`：

```
{ mode, controls: {n, chars, est}, targets: {n, chars, est}, frames: n,
  total_chars, total_est, omitted: {...} }
```

atlas 分支和 snapshot 分支各打一次。`est` 复用 `estimateTokens`（此时仍是旧口径，切片 6 才校准 —— 基线和对照用同一把尺子即可）。

**验**：真机跑一个含 3~5 次 read_page 的任务，把每次 `[read_page]` 和对应轮次的 `[ctx]` prompt 抄下来，作为**基线表**。后续每片改完重跑同一任务对比。

---

### 切片 1 — Atlas 执行 budget：controls/targets top-K + omitted + query

对应 P0.1。**预计吃掉本次优化 70% 的收益。**

**改 1**（`src/lib/dom-actions/probe-core.ts:1126` controls 循环）：每个 control 带一个 viewport 标记，一行成本（`getBoundingClientRect` 本来就要调）：

```js
const rect = el.getBoundingClientRect();
if (rect.bottom > 0 && rect.top < innerHeight && rect.right > 0 && rect.left < innerWidth) {
  control.inView = true;
}
```

`AtlasControl`（`page-atlas/types.ts`）加 `inView?: boolean`。

**改 2**（`src/lib/agent/tools/read-page.ts`）：`read_page` 参数加可选 `query?: string`。

**改 3**（`src/lib/agent/tools/page-atlas/render.ts`）：`renderPageAtlas` 接受 `{query?, maxControls, maxTargets}`：

- 有 `query` → 先按 `label`/`type` 子串过滤（大小写不敏感）
- 排序键：`inView desc` → 类型优先级（textbox/select/button > link > 其它，复用 `read-page.ts:129` 的 `interactivePriority` 思路）→ 原始顺序
- 取 top-K（默认 controls 40、targets 20）
- 尾部输出 `<omitted controls="444" targets="34" hint="..." />`，hint 明确写：`read_page({mode:"atlas", query:"关键词"})` 可定向召回被省略的控件

**改 4**：删掉 `<next_actions>` / `<next_action>` 整块（`render.ts:98-104`）。它是 `target.type` 的固定映射（collection/table → read_struct，其余 → read_target），54 条占 1388 tokens，且把 20 字符的 `atlas_id` 每个 target 重复一遍。规则移进 prompt 一句话。

**验**：
- 单测：造 500 controls 的 `PageAtlasState`，断言渲染行数 ≤ 40 且 `omitted` 计数正确；带 `query` 时命中项必须出现在结果里
- 真机：同一页面 `[read_page]` 的 controls est 应从 ~14400 降到 ~1500 量级

**风险**：top-K 漏召回。兜底是 `query` + `omitted` 计数（LLM 能看见"还有 444 个"）。这是本片唯一需要真机盯的行为变化 —— 观察 LLM 是否会因为找不到控件而卡住。

### 切片 2 — records 去重与去双重 escaping

对应 P0.5。

**改**（`src/lib/agent/tools/page-atlas/target-tools.ts`）：

1. `renderRecords`：`<text>` 只在 `record.fields` 为空时输出（region 类型的 record 只有 text 没 fields，那种情况才需要）。`evidence` 从独立元素改成 `<record>` 的属性。
2. `renderRecords` 的 `<fields>` 与 `renderExtractedRecords` 的输出：不再用 `xml(JSON.stringify(...))`（它把每个 `"` 变成 `&quot;`，单独造成 1.94× 膨胀）。改为 `escapeUntrustedWrappers(JSON.stringify(...))` 后只 escape `<`，保留裸引号。JSON 里 `<` 极少，`>`/`&` 在元素内容位置不需要转义。
3. `renderExtractedRecords` 从"一整个 escaped JSON 数组"改成 JSON Lines（每行一条 record 的 compact JSON），去掉外层数组括号和逗号，也让截断不会产生半个数组。
4. `selectedRecords` 无 `range` 时默认上限 50 条，超出时在 `<records>` 上打 `omitted="N"` + `hint="pass range like 50..100"`。

**验**：单测断言 25 rows × 8 fields 的渲染结果 chars 下降 ≥ 60%（文档合成测量是 2.81×）；`read_struct` 现有测试全绿。

### 切片 3 — mode 各自只返回声明的表示面

对应 P0.2。

**改**（`read-page.ts:459-466` observationParts 组装）：

| mode | interactive index | HTML blocks |
|---|---|---|
| `interactive` | ✅ | ❌ |
| `content` | ❌ | ✅ |
| `full` | ✅ | ✅ |

现状三者都是"两个都出"，mode 只改 byte cap —— 与 prompt 里的描述不符，LLM 即使正确选了轻模式也拿到不需要的内容。

**验**：单测断言 `mode:"interactive"` 的 observation 不含 `<untrusted_page_content`，`mode:"content"` 不含 `<interactive_index`。

**注意**：`elide-stale-observations.ts` 的 `BULK_MARKERS` 同时认这两个标记，任一存在都能正确切割，本片不影响 elide。

### 切片 4 — 修 stale-elision 误删 target evidence

对应 P0.4。

**问题**：`read_struct` / `read_target` / `find_target` 与 read_page 快照共用 `<untrusted_page_content>` wrapper（`target-tools.ts:223`），因此进入旧轮次后会被 `elideStaleObservations` 当作页面快照抹掉。但它们是**任务证据**（抽出来的记录、锁定的 target_id），比页面快照更该保留。

**改**（最小改法，不做 typed tool result 改造）：给这三个 tool 换专属 wrapper tag `<untrusted_page_records>`，`BULK_MARKERS` 自然不再命中。按 dual-list invariant 同步注册两处：
- `src/lib/agent/untrusted-wrappers.ts` 的 `UNTRUSTED_WRAPPER_TAGS`
- `src/lib/agent/page-snapshot.ts` 的 `WRAPPER_TAGS_LIST`

同时 `prompt.ts:87` 的 data-only tag 清单加一行。

**验**：新增测试 —— 一段含 `read_struct` 结果的历史过 `elideStaleObservations` 后，records 内容必须原样保留；同一段里的 read_page 快照仍被抹掉。（文档指出现有测试用了实现中不存在的 `<untrusted_struct_records>`，所以从没覆盖真实路径 —— 本片顺带把测试对上实现。）

### 切片 5 — Atlas control 直接可执行，去掉无条件 interactive reread

对应 P0.3。**纯 prompt 改动，但有一个前置验证。**

**前置验证（必须先做）**：确认 atlas 的 `pie_idx` 与 `mode:"interactive"` 的 `pie_idx` 同源可互换。两条路径都走 `stampLiveDom` 打 `data-pie-idx`（`probe-core.ts:733` / `:1331`），PR#152 已统一 probe/act 核心，但**没有测试锁这个 parity**。先补一个测试：同一 DOM 分别跑 `op:"atlas"` 和 `op:"snapshot"`，断言同一元素拿到相同 `pieIdx`。

**改**（`prompt.ts` READ_PAGE_GUIDANCE）：atlas 的 `<control>` 已带 `frame_id` + `pie_idx`，可**直接**用于 click/type/select；只有拿到 "Element not found" 或页面已变化时才 `read_page({mode:"interactive"})` 取新索引。同时补上切片 1 删掉的 next_actions 规则一句（collection/table → `read_struct`，detail_region/region → `read_target`）。

**验**：真机跑一个"读页 → 点击"的任务，观察是否还会多插一次 `mode:"interactive"` 调用。这是省一整次页面暴露。

### 切片 6 — estimateTokens 校准（独立归因，最后做）

调研文档 §8 提到"预算单位不一致"但未量化。本分支实测：

```
step 67  est 37113  vs  真实 prompt 61434   估算 = 真实的 60%
step 68  est 89795  vs  真实 prompt 167845  估算 = 真实的 53%
```

`estimateTokens` 系统性低估 40~47%，而 `compactReactWindow` 和 `applyTokenBudget` 的 80% 阈值判断全靠它 —— **它以为在 40%，实际已到 75%**。这不只是工具结果计数问题，现有对话窗口预算本身就是失准的。

**改**（`src/lib/agent/window-token-budget.ts:101`）：divisor 英文 `4 → 2.5`、CJK `1.5 → 1.2`。注释写明这是**安全上界**而非精确估计：低估的代价是 compaction 触发太晚（真实已超窗），高估的代价只是压得早一点。

**验**：跑一轮长任务，比对 `[ctx]` 的 `est` 与 `prompt`，误差应落在 ±15% 内。

**为什么放最后**：它会让 compaction 触发更早，改变对话窗口行为。跟 read_page 的改动混在一起会让收益无法归因。

## 不在本计划内

- **P0.6 collection/template 与 global controls 去重** —— 降级为观察项。切片 1 的 top-K 会间接挡掉大部分重复模板控件；真做归属去重要在 probe 侧建 control→target 关系，改动不小。**先看切片 1 之后 controls 还占多少**，如果只剩 1500 tokens 量级，这条就是无意义工作。
- **P1 Page Store / P2 检索层** —— 等 P0 数据。若 P0 后单次 read_page 已降到 3~5k tokens 量级，就不必付 MV3 生命周期的复杂度。
- **格式改造（JSON schema-once rows / TOON）** —— 调研文档自己的 benchmark 说明：仅换序列化只有 16% 降幅，真正跃迁来自降基数（top-40 从 26816 → 416 tokens）。切片 1 已经在做后者。格式改造留到基数问题解决后再按真实 tokenizer 评估。

## 验收

同一个真机任务，切片 0 的基线表 vs 全部做完后：

| 指标 | 来源 | 目标 |
|---|---|---|
| 单次 atlas observation tokens | `[read_page]` | 20881 → **< 4000** |
| read_page 轮次的 prompt 增量 | `[ctx]` | +106411 → **< 30000** |
| 任务成功率 | 人工 | 不下降 |
| 多插的 `mode:"interactive"` 调用次数 | 轮次日志 | 减少 |
| `est` 与真实 prompt 误差 | `[ctx]` | ±15% 内（切片 6 后） |

**任务成功率不下降是硬门槛。** top-K 和 records 上限都是有损操作，只降 token 但让 LLM 找不到控件不算成功。
